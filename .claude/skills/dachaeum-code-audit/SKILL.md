# 다채움 동의서 코드 검수

이 스킬은 **검수와 보고** 절차다. 문제를 찾아도 앱 코드를 자동으로 고치지 않는다.

## 0. 가장 먼저 지킬 것

1. **보고 먼저, 수정은 요청 후.** 오류를 찾으면 `문제 · 근거 · 영향 범위 · 수정안`을 보고하고 멈춘다.
   사용자가 해당 항목의 수정을 명시적으로 요청한 경우에만 `src/`·`data/`·`index.html`을 바꾼다.
2. **수정 전 원인 확인.** 증상만 보고 고치지 않는다. 원인 코드 위치를 찾고, 가능하면 수정 전 코드에서
   문제를 재현(테스트·시나리오)한 결과를 근거로 첨부한다. 재현하지 못했으면 그렇게 적는다.
3. **기준이 불명확하면 수정하지 않는다.** 가격·정상가·보관기간·삭제 범위·문구 등 정책 판단이 필요한 항목은
   추정값을 넣지 않고 `기준 확인 필요`로 분류한다.
4. **커밋·push·main 병합·병원 페이지 배포는 사용자가 요청할 때만.** 작업은 별도 브랜치에서 한다.
5. **실제 환자 정보·백업 파일은 저장소·테스트·보고서에 넣지 않는다.** 테스트는 가짜 환자 자료만 쓴다.

## 1. 확정된 규칙 (검수 기준 — 바꾸지 않음)

### 환불 계산
- **최종 환불금액 = MAX(0, 실제 납부액 − 계약 총액 × 10% − 이용금액)**
- 위약금 = **계약 총액(`total`) × 10%**. 예약금·현재 납부액·잔액 기준이 아니다. 예약금을 위약금으로 보지 않는다.
- 실제 납부액(`paid`) = 예약금 + 기납부 예약금 + 선결제권 사용분 + 이후 잔금 결제. `total`과 별도 값으로 저장·계산.
- 결과가 0원 이하면 0원. 음수 표시·추가 청구 전환 없음.
- 시술 시작 전/후 구분은 표시용이며 공식은 동일(이용금액 0이면 시작 전).

### 이용금액
- 항목별 **계약 당시 저장된 1회 정상가 × 실제 이용 수량**의 합. 프로그램 금액 ÷ 총 회차, 결제금액 비례 배분 금지.
- 흑자: 병변 1개 단위. 시술을 시작한 병변만 그 병변 금액 전액. 5등분 금지.
- 얼굴 점 CO₂ 제거: 병변별로 입력한 정상가 합(계약 1회 정상가 이상).
- 얼굴 전체 CO₂ 제거 추가옵션(PGM-0004/0006/0008/0010): 포함 1회 · 1회 정상가 110,000원 · 추가금 110,000원. 점 CO₂와 별도.
- 공통 총회차 상한(cap) 계약: 전체 이용 횟수가 상한을 넘지 않음.
- 서비스 기록: 염증주사(부위 구간별), 약처방(14일 미만 15,000 / 14일 이상 20,000), 알러지케어. 계약 당시 단가(`svcPrices`) 사용.
  같은 서비스가 프로그램 구성과 별도 기록에 중복 차감되지 않아야 함.

### 정상가 누락
- 0원으로 계산하지 않는다.
- 신규 계약: 가격표에 1회 정상가가 없는 구성은 직원이 입력해야 서명 가능. 입력값은 계약 항목에 저장(`unitInput`).
- 기존 계약: 이용 기록이 있는 항목에 정상가가 없으면 '정상가 확인 필요'로 환불 확정 차단. 이용하지 않은 항목으로는 차단하지 않음.
- 보완은 `priceFixes`(금액·근거·일시)로 별도 기록. 원 계약 항목·서명 문서는 바꾸지 않음.
- 계약 당시 서비스 단가가 없는 이전 계약에 현재 가격표 단가를 자동 적용하지 않음.
- PGM-0037·PGM-0106 남성 턱밑라인 포함 제모: 근거 확인 전까지 '정상가 확인 필요' 유지. 660,000 ÷ 5 등 추정 금지.

### 결제
- 할인은 하나만(일반·지인 5%·재티켓팅 10%·선결제권 300/400/500 = 10/15/20%), 이벤트·지정 결합가는 추가 할인 불가.
- 당일 결제 = 최종 계약금액 − 기존 선결제권 잔액 − 기납부 예약금. 예약금 결제는 계약 총액의 10%(남은 결제액 한도).
- 선결제권 신규 구매: 완납(선결제권 금액 전액) 또는 예약금 중 선택. **선결제권 예약금 = 선결제권 구매금액의 10%**
  (300만 원권 30만 원 · 400만 원권 40만 원 · 500만 원권 50만 원). 일반 계약의 예약금(계약 총액 10%)과 별개.
  선택 전·결제수단 미선택이면 서명 불가. 선결제권 선택만으로 완납 처리하지 않음.
  미수금 = 선결제권 구매금액 − 받은 금액. 저장(`prepaid.received`·`unpaid`·`payType`) 후 계약 목록·상세에서도 받은 금액·미수금을 표시하고,
  프로그램에 선결제권을 사용했다는 이유로 '완납'으로 표시하지 않음. 미수금을 나중에 받는 기능은 별도 결정 전까지 없음.
- 잔금 결제는 결제내역(`payments`, `balance: true`)에 추가하고 `paid`에 누적. 전액 납부 시 완납. 남은 잔금 초과 기록 불가.
- 결제수단별 환불: 수단별 원결제 금액 초과 금지, 합계 = 최종 환불금액, 프로그램이 자동 배분하지 않음.
  선결제권 잔액 복구·기납부 예약금은 별도 줄. 결제수단 1개여도 원결제 초과 차단.

### 계약·상태
- 상태는 **등록완료 / 환불완료** 두 가지뿐. 새 상태를 추가하지 않는다.
- 환불 정산서 서명 저장 성공 = 환불완료. 그 전에는 등록완료.
- 환불완료 후에는 환불 정산·잔금 기록·재서명 불가.
- 이전 버전의 중간 상태값(환불정산중·환불서명대기·환불처리대기)은 서명된 정산서가 있으면 환불완료, 없으면 등록완료로 읽는다.
- 서명 시점의 계약 값(환자·프로그램·항목·1회 정상가·할인·결제·서비스 단가·약관 버전·이용기간)은 고정. 이후 가격표·가격 관리 변경이 기존 계약을 바꾸지 않음.
- 문서는 계약 id(`contractId`)로 연결·버전 관리. 재서명은 화면 구성이 저장된 계약과 같을 때만, 이전 버전은 보존.

## 2. 기존 저장 데이터 보존 원칙
- 기기 저장 키: `dachaeum.v3.contracts`, `dachaeum.v3.docs`, `dachaeum.priceOverride`, `dachaeum.selection`, `dachaeum.v3.lastBackup`.
- 수정은 이전 형식 데이터를 그대로 읽을 수 있어야 한다(필드 추가는 선택값으로, 이름 변경·삭제 금지).
- 서명된 동의서·환불 정산서·계약·결제·이용기록·환불 계산내역·보완 기록을 삭제·덮어쓰기하지 않는다. 환자 삭제 기능은 차단 상태 유지.
- 저장 형식을 바꾸는 수정은 기준 확인 필요로 분류하고, 이전 데이터 변환 방법을 수정안에 함께 적는다.
- 다른 앱(재고관리 `inventory-system:*`) 저장 자료를 읽거나 바꾸지 않는다.

## 3. 검수 절차

1. **범위 확인**: 대상 브랜치·커밋, 검수 영역을 적는다.
2. **원본 기준 확인**: 수정은 `src/`·`data/`가 기준이고 `index.html`은 `npm run build` 결과다.
   `python3 tools/build.py /tmp/check.html && cmp index.html /tmp/check.html`로 원본과 번들이 일치하는지 먼저 본다.
3. **코드 읽기**: 아래 4~6장 체크리스트를 따라 해당 함수를 읽는다
   (`src/refund.js` settle·refund·resolvePrices·checkAlloc·refundPays, `src/pricing.js` discount·payment,
   `src/app.dc.js` buildContract·saveSig·saveRefund·saveDraft·saveContract·statusOf·rfStateOf·잔금·백업).
4. **테스트 실행**: `npm test` (원격 환경은 `NODE_PATH=$(npm root -g) npm test`). 실패는 숨기지 않고 그대로 보고.
5. **재현**: 의심 항목은 가짜 자료로 시나리오를 만들어 재현한다(Node 단위 테스트 또는 Playwright).
6. **보고**: 8장 형식으로 보고하고 멈춘다. 수정 요청을 받으면 7장 절차를 따른다.

## 4. 계산식 검증 기준
- 최소 사례(테스트 `test/refund.test.cjs`가 고정):
  시작 전 / 시작 후 / 0원 미만 → 0 / 예약금만 / 예약금 + 잔금 / 흑자 병변 일부 시작 / CO₂ 병변 /
  서비스 기록 / cap 계약 / 선결제권만 결제 / 기납부 예약금 / 정상가 누락(이용·미이용) / 보완 후.
- 화면 표시값과 저장값(`contract.refund`)과 계산값(`RF.settle`)이 모두 같은지 확인한다.
- 동의서·환불 정산서·화면 문구가 1장 규칙과 같은지 확인한다(예: 위약금 기준 문구, '실제 납부금액 − 위약금 10%').
- 금액은 표시 문자열이 아닌 숫자로 계산되는지, 쉼표·'원' 포함 문자열·빈 값에서 NaN·문자열 이어붙이기가 없는지.

## 5. 입력값·예외값 검증
- 금액 입력: 빈 값, 문자, 0, 음수, 소수, 쉼표·'원' 포함, 매우 큰 값.
- 이용 수량: 0 아래로 내려가지 않음, 등록 수량·cap 상한, 추가 부위는 상한 없음.
- 결제: 분할결제 금액 누락·초과, 결제수단 미선택, 잔금 초과, 결제 정보 수정 중 잔금 기록 차단.
- 정상가 보완 prompt: 취소·빈 값·문자·0원·음수·소수·근거 없음·최종 확인 취소 → 저장 안 됨, 여러 항목 중 하나라도 취소되면 전부 저장 안 됨.
- 중복 클릭: 동의서 저장·환불 정산서 저장·잔금 기록이 2번 저장되지 않음.
- 이전 환자 입력값(기납부 예약금·결제수단·할인·구성 선택)이 다음 환자 작성에 남지 않음.
- 손상·누락 데이터(필드 없음, 문자열 금액)에서 화면이 깨지지 않고 확정이 막히는지.

## 6. 상태·저장 흐름 검증
### 서명 전후 상태 전환
- 새 계약 서명 전: 계약 없음(서명대기 표시만) → 서명 저장 후 등록완료, 문서 v1 저장.
- 환불 정산 입력 중: 상태 등록완료 유지, 작성값만 `refundDraft`에 저장.
- 정산서 서명 화면 진입 조건: 오류(정상가 확인 필요·배분 불일치·병변 입력 오류) 없을 때만.
- 정산서 서명 저장 후: 환불완료, `refund`(계산내역·결제수단별 환불·보완 기록) 저장, `refundDraft` 비움, 정산서 문서 저장.
- 환불완료 후: 정산·잔금·재서명 버튼 없음.

### 새로고침·재접속·백업·복원
- 입력 직후 새로고침·앱 닫기·다른 앱 전환 후에도 작성 중 정산이 복원됨(계약별로 분리).
- 계약 A·B를 오가도 이용 기록이 섞이지 않음.
- 백업: 이 앱 자료 전체 포함, 파일 안에 환자정보 평문 없음, 백업 후 기존 자료 불변.
- 복원: 형식·버전·비밀번호·검증값·누락·중복·문서-계약 연결 검사. 기존 자료가 있으면 교체 안내 후 확인, 합치지 않음.
  잘못된 비밀번호·변조·다른 형식 파일은 기존 자료를 바꾸지 않음. 쓰기 실패 시 원래 자료로 롤백.
  복원 후 계약·문서·금액·상태·작성 중 정산·가격 관리 설정이 원본과 동일, 재고관리 자료 불변.

## 7. 회귀 테스트와 수정 절차 (수정 요청을 받은 경우에만)
1. 요청받은 항목만 수정한다. 범위를 넓히지 않는다.
2. 수정 전 코드에서 **실패하는 테스트**를 먼저 추가해 원인을 증명한다.
3. `src/`·`data/` 수정 → `npm run build` → `npm test` 전체 통과 확인.
   `data/programs.json`은 `json.dumps(indent=2, ensure_ascii=False)` 형식을 유지해 바뀐 줄만 diff에 남긴다.
4. 기존 테스트(새 계약·재서명·환불 흐름·계약 분리·작성 중 복원·잔금·이전 상태값·백업·복원·삭제 차단·표시 문구)가 모두 다시 통과해야 한다.
5. 커밋·push·병합은 사용자가 요청할 때만.

## 8. 보고 형식
검수 결과를 아래 4가지로만 나눈다. 각 항목에 `문제 · 근거(파일·함수·재현 결과) · 영향 범위 · 수정안`을 적는다.

- **수정·검증 완료**: 사용자 요청으로 수정했고 테스트로 확인한 항목.
- **미수정**: 오류로 확인했지만 아직 수정 요청을 받지 않은 항목 (수정안 포함).
- **기준 확인 필요**: 가격·정책·문구 등 기준이 불명확해 판단할 수 없는 항목 (확인할 질문 포함).
- **테스트 미실행**: 실행하지 못한 검증과 이유. 실제 iPad Safari, 실제 병원 자료, 대용량 자료 등.
  Chromium 통과를 Safari 검증으로 표시하지 않는다.

테스트 결과는 `통과 n건 / 실패 n건`으로 적고, 실패는 그대로 보고한다.
